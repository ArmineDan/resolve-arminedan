# Tags & Canned Responses

## Context

Resolve (v0 "Core Tickets") lets agents create tickets, change status, and
leave comments, but has no way to categorize tickets or reuse boilerplate
replies. Class 3 ("context kit + tags/canned responses") adds two small,
independent pieces of agent tooling on top of the existing ticket:

- **Tags** — free-text labels an agent can attach to or remove from a
  ticket, used to categorize/filter tickets (e.g. `billing`, `bug`,
  `vip`).
- **Canned responses** — a small catalog of reusable reply text an agent
  can pick from when adding a comment, so repeated answers don't have to
  be retyped.

Both features slot into the existing `TicketsModule` conventions:
controller → service → repository layering, mandatory audit trail on every
mutation, service-layer validation that throws `BadRequestException`
naming the offending field, dialect-neutral entities (ISO-string dates,
app-generated ids), and actor sourced from the `X-Actor` header.

## Acceptance Criteria

- **AC-1**: `POST /tickets/:id/tags` with body `{ "name": "billing" }`
  attaches the tag to the ticket and returns `201` with the updated
  ticket, including a `tags` array of tag names.
- **AC-2**: Attaching a tag whose name already exists on that ticket
  (compared case-insensitively) returns `400` naming the field `name`;
  the ticket's tag set is unchanged.
- **AC-3**: `DELETE /tickets/:id/tags/:name` removes the tag from the
  ticket and returns `200` with the updated ticket. If the ticket has no
  tag matching `:name` (case-insensitively), the response is `404`.
- **AC-4**: `GET /tags` returns `200` with the list of distinct tag names
  currently attached to at least one ticket, sorted alphabetically.
- **AC-5**: Every successful tag attach/detach writes one audit entry via
  the existing audit trail: action `ticket.tag_added` or
  `ticket.tag_removed`, with `details: { tag: <name> }`.
- **AC-6**: `GET /canned-responses` returns `200` with the list of canned
  responses (`id`, `title`, `body`), sorted by `title`.
- **AC-7**: `POST /canned-responses` with body
  `{ "title": ..., "body": ... }` creates a canned response and returns
  `201`. Empty/whitespace-only `title` or `body` returns `400` naming
  that field. A `title` that already exists (case-insensitively) returns
  `400` naming the field `title`.
- **AC-8**: `DELETE /canned-responses/:id` deletes the canned response
  and returns `200`; returns `404` if no canned response with that id
  exists.
- **AC-9**: `POST /tickets/:id/comments` accepts an optional
  `cannedResponseId` field. When present and valid, the created comment's
  `body` is set to that canned response's current `body` (the request's
  own `body` field, if any, is ignored). An unknown `cannedResponseId`
  returns `400` naming the field `cannedResponseId`.
- **AC-10**: The audit entry for a comment created from a canned response
  (`ticket.commented`) includes `cannedResponseId` in `details` in
  addition to the existing `commentId` and `internal` fields; comments
  created without one omit it, matching today's `details` shape.
- **AC-11**: Deleting a canned response does not alter the `body` of
  comments already created from it (comment bodies are copied at
  creation time, not referenced live).
- **AC-12**: A ticket cannot have more than 10 tags attached at once.
  Attaching an 11th tag returns `400`; the ticket's tag set is unchanged.

## Invariants

- A ticket's tag set never contains two names that are equal
  case-insensitively.
- A ticket's tag set never exceeds 10 tags.
- Canned response titles are globally unique, compared
  case-insensitively.
- A comment's `body` is always a concrete, persisted string — never a
  live pointer to a canned response.
- The `internal` visibility rule for comments (internal-only notes must
  never be exposed to customers) applies identically to comments created
  from a canned response.
- Every tag attach/detach and canned-response create/delete is
  attributable to an actor and produces exactly one audit entry, per the
  existing "audit trail is mandatory for mutations" rule.

## Constraints

- New columns/entities follow the existing dialect-neutral style: string
  ids generated by `newId()` (e.g. `cnd_xxxxxxxx`), dates as ISO strings,
  no native timestamp/array/enum column types that behave differently
  between PostgreSQL and `better-sqlite3`.
- Validation stays in the service layer as explicit checks throwing
  `BadRequestException` naming the offending field — no class-validator
  DTOs, consistent with `tickets.service.ts`.
- Actor for audit entries comes from the `X-Actor` request header
  (default `'api'`), matching `TicketsController`.
- No TypeORM migrations; schema changes rely on `synchronize: true`.
- Controllers stay thin; all new business logic and validation lives in
  service classes, with data access only through repository classes (no
  direct `DataSource`/`Repository` use in services).

## Non-Goals

- Tag colors, categories, hierarchies, or per-tag permissions.
- Tag autocomplete/suggestion beyond the plain alphabetical `GET /tags`
  listing.
- Canned response variables/placeholders (e.g. `{{customerName}}`) —
  bodies are static text only.
- Editing an existing canned response's title/body (only create and
  delete are supported in v0).
- Usage analytics or reporting on which tags or canned responses are used
  most.
- Any change to customer-facing visibility: tags and canned responses are
  agent-only tooling, and internal comments remain excluded from any
  future customer-facing view exactly as today.
- SLA engine, triage automation, or any other later-class roadmap item
  interacting with tags (e.g. auto-tagging).

## Open Questions

- Should tag names be normalized to a single case for storage/display
  (e.g. lowercased), or stored case-preserving with only comparisons done
  case-insensitively?
- Should a tag that's been detached from every ticket disappear from
  `GET /tags` immediately (derived from current ticket state), or should
  tags live in a persistent catalog independent of ticket attachment?
- Should a canned response be allowed to pre-set the `internal` flag on
  the resulting comment (e.g. "internal-only" canned responses), or does
  the agent always choose `internal` explicitly regardless of which
  canned response is used?
